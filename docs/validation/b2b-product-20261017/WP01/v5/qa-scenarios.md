# Amendment008 UI scenarios for QA

These are requested scenarios, not authored cross-feature specs or executed browser acceptance. Preserve matching Playwright1.63, Chromium/WebKit 320x740, 430x932 touch and 1440x1000, unified/white-label, two brands/four branches and all current security settings.

1. Select a real organization admin/superadmin and open People. Branch discovery must show server-provided names/IDs from that organization only. Switch to a coach/member function on the same identity: no administrative invitation form or broader role options remain. Delay bootstrap, then switch account/realm/branch; the old catalog must never repopulate.
2. With organization role member, explicitly select `Entrenador en [branch]` inactive and `Socio en [other branch]` active, then both roles on one branch. Verify no role-derived/default grant and the exact unique array/order/flags in the sent request and persisted snapshot. Repeat with organization admin/superadmin plus explicit branch functions; organization role remains independent.
3. Begin with every role selector at `No incluir esta función`. Explicitly check the no-grants confirmation; creation sends exactly `[]`, never Principal/current-branch fallback. Verify the consequence text and accepted no-grants summary. Changing the organization role does not change the array.
4. Lose the creation response after commit. Fields freeze; explicit retry uses the exact invitation ID, operation ID, revision, email/role and branch array. It creates no duplicate. A changed-operation raw request must conflict; the UI announces the rejection and does not perform blind retry. On successful retry, fields/grants reset and the issued grant summary remains beside the private link.
5. Revoke/archive a selected branch after discovery, then create/accept. No alternative grant is inferred. Show the precise denial, reload choices, retain unavailable selections as errors and require explicit removal/change. Branch catalog failure cannot appear as a successful empty/default branch list. Already-archived initial discovery requires the owner metadata seam in owner-requests.md; do not mark that case passed with guessed fixtures.
6. Existing B2B account accepts through its own password/consent, existing membership cannot be promoted/reactivated, expired/used invitation fails, and fresh realm admission replaces an older mounted actor in the same tab. These actual acceptance journeys remain root/QA-owned; the People UI's synthetic tests are not their proof.
7. At each viewport verify associated labels for both branch role selectors and active/inactive/none values, keyboard selection and visible focus, 44px controls, wrapped long branch names/IDs, no horizontal overflow, exact count/issued-permission summaries, and no accidental submit from Reload buttons.
8. Scope/role/tenant denial must clear roster, catalog and private link. A temporary root disconnect hides projections; fresh authorization/discovery precedes further edits. Preserve pending operation bytes only for explicit authorized retry in the same lifetime.

No health consent is granted by a branch/organization role alone. These scenarios authorize synthetic fixtures only, not actual invitation sends or production account creation.
