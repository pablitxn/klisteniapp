## Safe first-wave contracts and actual product gates

These are concrete proposals for the coordinator's owner-repo plan, not implemented changes or newly confirmed product choices.

1. **Q01 scope:** preserve organization as customer/brand and explicit branch authorization. Existing owner ADR `docs/b2b-white-label-decisions.md:13-17,50-61,74-95` explicitly prohibits Centro-only trainer editing Norte and implicit trainer aggregation. The new d01 replaces assigned-member restriction, not this isolation by implication. Execute same-branch shift coverage first: active org membership + active selected branch + explicit coach grant → all member users/plans/histories in that branch; remove assignment EXISTS only from that scope. Preserve composite org/branch filters for roster, target lookup, assignments, history, program writes, reports and media. Coach assignments may remain informational responsibility metadata. Brand-wide trainer access across ungranted branches is a genuine unresolved Q01 expansion. A branchless legacy context (`white-label-access.ts:63`) currently yields NULL repository branch predicates; do not globally delete assignment filters there until explicitly bound to Principal or adopted scope. Add negative branchless tests.

2. **Superadmin:** use distinct organization membership `superadmin`; keep platform operators separate. Superadmin inherits admin capabilities and may create admin/coach/member; admin creates coach/member. No default platform/domain/service/module-ceiling powers. Existing full brand admins already create admins and manage brand-wide grants: deterministic migration to org-superadmin is a capability-preserving candidate, not automatic elevation into `b2b_platform_admin`. Record that disposition in owner ADR and migration tests. Keep last privileged administrator invariant; replace scattered `role === 'admin'` checks with explicit capability predicates and exhaustive schemas. An alternative preserving old admin records while removing their powers is a migration breaking change requiring explicit disposition. Nothing establishes which named human should receive platform access.

3. **Audit:** extend transactionally with org, branch if operational, actor, action, target type/ID, prior/new revision and whitelisted changed-field values or immutable revision links, server timestamp and request/idempotency ID. Do not log raw health payloads/secrets. UI can display actor/action/time/diff against revision links. Audit purpose/visibility/retention should be explicit owner spec; no invented legal retention requirement. Period/stage/log mutations from A03/A05 must use the same audit helper, not only old program endpoints.

4. **Health ownership/import boundary:** choose one B2B personal-health owner identity keyed by authenticated user, independent of gym prescription storage and B2C subscription. Reuse normalized health semantics through a deliberately selected pure shared package or adapter, without importing the B2C store/app into B2B. Keep `klisteniapp.health` v1 valid. Define `manual file → adapter(format/version) → normalized records → existing validation/preview → explicit user confirmation → owner-scoped save`; unknown formats reject without writes. Anonymized samples only gate new external adapters, not JSON reuse or consent implementation. No background provider jobs or credentials are needed.

5. **Consent proposal:** default no grant; explicit owner action creates versioned grant keyed owner+organization+declared trainer audience, with declared record categories/purpose and granted/revoked timestamps. Exact trainer-vs-gym audience and category granularity are Q06 contract choices; deny outside explicit grant. Every trainer read/export/report/media path intersects active trainer scope + target scope + live consent; admin/superadmin status alone supplies no health access. Recheck grant within serialized authorization transaction to order queued read/export vs revoke; never embed health in immutable gym program/session snapshots. Grant/revoke settings stay reachable to owner when gym access is inactive. Revocation increments version, invalidates queries, clears app-controlled cache, cancels pending results and denies new trainer offline caching/exports. Reconnection reauthorizes before rendering or syncing. Already received/exported bytes cannot be technically recalled; do not promise otherwise. A defensible initial delivery avoids persistent trainer health offline copies, with fail-closed handling when live consent cannot be verified. Do not equate existing invitation `consent:true` with health consent.

6. **Inactive/session contract:** separate authentication/brand binding from operational membership entitlement. Keep exact host+org+domain generation checks; allow a known inactive membership to bind only a restricted personal-export session capability. Missing/foreign memberships still reject generically. `me` must return restricted membership status/capabilities rather than omit it. Route allowlist: own record export, own consent control if health exists, separate B2C invitation and essential account session controls; deny gym catalog/routine/editor/report/write/media routes. Do not loosen `m.active` globally. Export can reuse historical execution snapshots but should define versioned complete personal record coverage; never export other members or trainer-only private notes. No automatic B2C account, billing, identity linking, routine conversion or data transfer.

7. **History/reactivation:** define operational target access separately from historical target access, so inactive records stay visible to permitted gym staff without restoring gym features to the member. Preserve snapshots/FKs/data on state change. Membership reactivation restores existing still-valid branch grants and records; intentionally revoked branch grants remain revoked. New coach coverage removes dependence on deleted responsibility relationships. Do not let old operational sessions/offline queues bypass state change: entitlement version/recheck before every operation, purge sensitive views, reject stale pending writes and recover retained drafts safely.

8. **B2C compatibility:** retain separate apps, DBs, sessions, storage and billing. Version a product-neutral prescription/session interchange or explicit adapter where needed; do not declare current PersonalRoutine/ProgramStep schemas equivalent or auto-convert gym records. Owner specs and `check-b2b:boundaries` must be updated together if a pure shared health/training package is selected. Paid destination configuration and any explicit transfer/onboarding choice remain Q07; invitation UI/deny-by-default entitlement work can proceed before a transfer mechanism exists.
